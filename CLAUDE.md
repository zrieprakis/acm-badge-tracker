# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A web dashboard that shows, per tracked team member, the last door they badged into via an on-prem Avigilon Access Control Manager (ACM) server. The backend polls ACM on an interval and caches "last known location" per person; the frontend shows it with a short auto-refresh delay.

Real ACM integration (`ACM_CLIENT_MODE=live`, via `AvigilonAcmClient`) is implemented and has been verified against a live appliance - see the detailed notes under "Real Avigilon ACM integration" below before touching that file. `ACM_CLIENT_MODE=mock` (the default) runs everything against `MockAcmClient`, which simulates cardholders and access events with no network calls.

**This is deployed and running in production** on `speedsupsrvr.hammond.k12.in.us` (a Windows server running Docker Desktop, on the district's internal network), tracking a real team's real badge activity against the real ACM appliance. There is no separate staging environment - local `npm run dev:*` and a local `docker compose up` are for development/testing only, always against `ACM_CLIENT_MODE=mock` unless you have a specific reason to point at the real appliance (and if you do, use test data, not the production roster).

## Commands

npm workspaces monorepo: `shared`, `backend`, `frontend`. Run all commands from the repo root unless noted.

```bash
npm install                      # installs all three workspaces

npm run build                    # builds shared -> backend -> frontend, in that order
npm run build --workspace=shared # shared MUST be rebuilt after editing shared/src/types.ts -
                                  # backend/frontend import its compiled dist/, not the source

npm run dev:backend              # tsx watch, backend on :3001 (requires env vars, see below)
npm run dev:frontend             # vite dev server on :5173, proxies /api to :3001

npm run test                     # runs backend vitest suite (only workspace with tests)
npm run test --workspace=backend -- path/to/file.test.ts   # single test file
npx vitest run -t "test name"    # (from backend/) run tests matching a name pattern

npm run lint                     # eslint . --ext .ts,.tsx
npm run format                   # prettier --write .

# from backend/:
npm run db:generate              # drizzle-kit generate - regenerate SQL migration after editing schema.ts
npm run db:migrate               # apply migrations to DB_PATH
npm run db:seed                  # runs migrations, then seeds an admin user + sample roster (see below)
```

### Required environment variables (backend)

`backend/src/config/env.ts` validates env vars with zod at startup and **exits the process** if invalid. `SESSION_SECRET` (>=16 chars) is the only one with no default. Copy `.env.example` to `.env` for Docker; for local `npm run dev:backend`, export vars directly or the process will exit immediately. Useful ones for local dev:

```bash
ACM_CLIENT_MODE=mock            # or "live" (see "Real Avigilon ACM integration" below)

SEED_ADMIN_USERNAME=admin       # only read by db:seed, not the server itself
SEED_ADMIN_PASSWORD=...
```

### Docker

`docker-compose.yml` builds `backend/Dockerfile` and `frontend/Dockerfile` (both multi-stage, context is repo root since they need the `shared` workspace). Requires a real `.env` at repo root (`env_file: .env` on the backend service - compose fails fast if it's missing, which is intentional). SQLite lives in the `db-data` named volume. Frontend's nginx serves the built SPA and proxies `/api/*` to the `backend` service. Verified end-to-end via `docker compose up -d` (build, login through the nginx proxy, and data surviving `down && up` against the named volume) - `db:seed` needs to be run manually once against a fresh volume (`docker compose exec -e SEED_ADMIN_USERNAME=... -e SEED_ADMIN_PASSWORD=... backend node dist/db/seed.js`), it isn't run automatically like migrations are.

**See `DEPLOY.md` at the repo root for the step-by-step runbook to ship a code change to production** - it's the `docker save`/`docker load` workflow described by the bullet points below, written up as a repeatable checklist (build images locally, save/copy/load onto the production host, `docker compose up -d`) that preserves the existing `db-data` volume. Keep it in sync if the deploy process here changes.

- Both Dockerfiles must `COPY tsconfig.base.json` alongside `package.json`/`package-lock.json` in the build stage - `shared/tsconfig.json` extends it, and without it `tsc -p tsconfig.json` fails inside the container (`TS5083: Cannot read file '/app/tsconfig.base.json'`) even though it works fine outside Docker where the file is just already present on disk.
- `express-session` only sets the cookie's `Secure` flag when `NODE_ENV=production`. Testing the compose stack over plain HTTP without TLS requires `NODE_ENV=development` in `.env`, or login will return 200 but the browser/curl will silently refuse to persist the session cookie.
- **TLS is wired up**: `frontend/nginx.conf` terminates real TLS for `speedsupsrvr.hammond.k12.in.us` using a self-signed cert in `SelfSigned/` at the repo root (git-ignored - it contains a private key, never commit it). Port 80 is redirect-only (`301` to `https://`); the app is only ever served over 443. `docker-compose.yml` mounts `SelfSigned/` read-only into the frontend container at `/etc/nginx/certs` rather than baking the key into the image, same reasoning as `.env`. `NODE_ENV=production` in `.env` depends on this - if this ever gets torn out (e.g. testing on bare `http://localhost` again), flip `NODE_ENV` back to `development` or logins will silently fail to persist a session. Current cert is valid until Sept 2036.
- **`backend/src/app.ts` sets `app.set('trust proxy', 1)`.** Without it, `NODE_ENV=production`'s secure cookie silently never gets sent to the browser - no error anywhere, login just returns 200 and nothing logs in - because Express sees the nginx->backend hop (plain HTTP inside the docker network) as insecure and won't set a `Secure` cookie on what it thinks is an insecure connection, even though the actual client connection was HTTPS. `trust proxy: 1` tells Express to trust nginx's `X-Forwarded-Proto` header for exactly one hop of proxying. Found by testing the real login flow end-to-end over HTTPS, not just checking that nginx served a 200 - worth remembering if this class of bug ever resurfaces after touching the proxy chain.
- **Rotating the cert** (self-signed expired, or swapping in a CA-issued one): only `SelfSigned/cert.pem` and `SelfSigned/key.pem` are actually read (by `frontend/nginx.conf`'s `ssl_certificate`/`ssl_certificate_key`) - the `.crt`/`.p12`/`.pfx` copies in that folder are for other consumers and aren't used by this app.
  1. Replace `SelfSigned/cert.pem` and `SelfSigned/key.pem` with the new cert/key (same filenames).
  2. `docker compose restart frontend` - no rebuild needed, since the folder is a live-mounted volume rather than baked into the image.
  3. Verify the *live* connection is actually presenting the new cert (not just that the file on disk changed - nginx caches loaded certs per-worker at startup): `openssl s_client -connect <host>:443 -servername speedsupsrvr.hammond.k12.in.us </dev/null | openssl x509 -noout -dates`.
  - To generate a new self-signed cert/key pair matching the current one's shape: `openssl req -x509 -newkey rsa:2048 -keyout key.pem -out cert.pem -days 3650 -nodes -subj "/CN=speedsupsrvr.hammond.k12.in.us" -addext "subjectAltName=DNS:speedsupsrvr.hammond.k12.in.us,IP:10.1.248.192"`.
- **Both images and the `db-data` volume have explicit, stable names** (`acm-badge-tracker-backend`/`-frontend`, `acm-badge-tracker-db-data`) rather than Compose's default `<project-dir-name>-*`/`<project-dir-name>_db-data`. This was specifically to support deploying by `docker save`/`docker load`-ing pre-built images onto the production host rather than cloning+building there - without explicit names, an image or volume built/created under one folder name isn't recognized as a match under a different one, so Compose would silently try to rebuild (or a helper container couldn't reliably target the volume by name).
  - **Gotcha hit for real during the production migration**: renaming an *existing* volume this way doesn't migrate it - Compose creates a new, empty volume under the new name and orphans the old one under its old name. If you ever rename the volume again on a host with real data under the old name, copy the data across manually first: `docker run --rm -v <old-volume>:/old:ro -v <new-volume>:/new alpine cp -a /old/. /new/`.
  - **Seeding/replacing the DB on a host via the named volume** (e.g. migrating data to a fresh deployment): `docker run --rm -v acm-badge-tracker-db-data:/data -v <host-dir-with-file>:/backup alpine cp /backup/acm-tracker.db /data/acm-tracker.db`, then `docker compose restart backend`. The file will land owned by root (the helper container's default user) but the backend runs as a non-root `node` user (uid 1000) - fix with `docker run --rm -v acm-badge-tracker-db-data:/data alpine chown -R 1000:1000 /data` before restarting, or the backend will crash-loop on startup unable to open its own database.
- **Docker Desktop on Windows doesn't behave like a Linux service** - it only starts when a user interactively logs in (its own "start on login" setting), not on bare system boot. On the production host, this means a server reboot with nobody logged into the console leaves the containers down (not crash-looping - the engine itself never started, so `restart: unless-stopped` has nothing to act on) until someone logs in. Mitigated via a Windows Task Scheduler task ("At startup" trigger, "Run whether user is logged on or not") that launches `Docker Desktop.exe` without needing an interactive session. If this app ever needs stronger unattended-uptime guarantees than that, the real fix is running Docker Engine directly (e.g. inside WSL2) rather than through the Docker Desktop GUI shell.

## Architecture

### Workspace boundaries

- **`shared/`** - DTO types only (`shared/src/types.ts`), consumed by both backend and frontend as `@acm-tracker/shared`. It's resolved via its built `dist/`, not source, so **edits to shared types require `npm run build --workspace=shared` before backend/frontend will see them** (tsx/vite do not transpile across workspace package boundaries).
- **`backend/`** - Express API + polling scheduler + SQLite (via libSQL).
- **`frontend/`** - React SPA (Vite, React Router v7).

### Backend: layering rules

- **`acm/`** is the only code allowed to know Avigilon's real request/response shapes. Everything else depends only on the `AcmClient` interface (`authenticate`, `listCardholders`, `getRecentAccessEvents(cardholderIds, since)`). `acmClientFactory.ts` picks `MockAcmClient` or `AvigilonAcmClient` based on `ACM_CLIENT_MODE`.
- **`repositories/`** is the only code allowed to import the Drizzle client/schema directly. `services/` and `routes/` go through repositories, never raw queries - this is what would make a future Postgres swap mechanical if this ever outgrows SQLite.
- **`polling/pollService.ts`** orchestrates one poll cycle: fetch active roster from `teamMemberRepository`, pass their `acmCardholderId`s to `AcmClient.getRecentAccessEvents(cardholderIds, since)` where `since` is `sync_metadata.lastSuccessfulPollAt` (falls back to a 24h lookback on first run), match returned events back to team members by `acmCardholderId`, upsert `last_access_events` + append `access_event_history` via `accessEventRepository`, prune history older than `HISTORY_RETENTION_DAYS`, then update `sync_metadata`. `scheduler.ts` wraps this in a `setInterval` with an overlap guard (skips a tick if the previous cycle is still running). `runPollCycle()` takes an optional `AcmClient` param specifically so tests can inject a configured `MockAcmClient` or a client that throws, without touching the factory/env.
- **DB**: SQLite via `@libsql/client` + Drizzle ORM - **not** `better-sqlite3`, deliberately, because `better-sqlite3`'s native build failed on this dev machine (no MSVC toolchain, no prebuild for the Node version in use). `@libsql/client` ships prebuilt binaries and needs no compiler. `db/schema.ts` is the single source of truth for tables; after editing it, run `db:generate` to produce a new migration under `db/migrations/`, which `runMigrations()` applies automatically on backend startup (also callable directly via `db:migrate`). The build script copies `src/db/migrations/` (SQL + drizzle-kit's `meta/` folder) into `dist/db/migrations/` since `tsc` doesn't copy non-`.ts` assets - if migrations ever stop being found at runtime, check that copy step first.
- **Sessions**: a custom `LibsqlSessionStore` (`auth/libsqlSessionStore.ts`) backs `express-session`, storing sessions in the same libSQL database (`sessions` table) rather than pulling in a second native-dependent package (`connect-sqlite3`/`sqlite3`). `requireAuth` middleware protects everything under `/api` except `/api/auth/login` and `/api/health/ping`. Login timing is constant-time between "wrong password" and "user doesn't exist" via `passwordService.compareAgainstHashOrDummy`.
- **Login rate limiting**: `auth/loginRateLimiter.ts` locks a *username* out for 5 minutes after 3 failed attempts (429, checked before the password comparison even runs), independent of source IP - this app has a small fixed set of admin accounts, so protecting the credential is what matters, and IP-based limiting would be trivially bypassed by rotating IPs while also being bypassable-in-reverse (shared-IP staff networks locking each other out). State is an in-memory `Map` (resets on process restart) - intentionally not persisted to the DB to avoid a table for this; revisit if that resat-on-restart behavior ever becomes a real problem. The class takes `maxFailedAttempts`/`lockoutDurationMs` as constructor options specifically so tests can use tiny values instead of the real 3/5-minute ones.
- **Change password**: `PUT /api/auth/password` (`requireAuth`-protected, unlike `/auth/login`) takes `{ currentPassword, newPassword }`, re-verifies the current password the same way login does, and enforces a 12-character minimum on the new one. No multi-admin-account UI exists by design - this app is meant for one shared admin credential. Reachable in the frontend by clicking the username in the nav bar (`pages/AccountPage.tsx`).
- **Roster deletion has two tiers**: `DELETE /api/team/:id` soft-deletes (`isActive=false`, preserves history) by default; `DELETE /api/team/:id?hard=true` permanently removes the row (cascading to its `last_access_events`/`access_event_history` rows). Soft-delete is for routine offboarding; hard-delete is for correcting a mistaken roster entry (wrong badge number typo'd in, etc.) - both are exposed as separate "Deactivate"/"Delete" buttons in `RosterTable.tsx`, not one destructive action.
- **`DashboardEntryDTO` includes a "previous" event** (`previousDoorName`/`previousEventTimestamp`) alongside the current one, shown in smaller text under the current door in `TeamMemberCard.tsx`. `accessEventRepository.getPreviousEvents()` fetches it with one query per team member (not a window function) - the second-most-recent row per person in `access_event_history`, since the most-recent row there always duplicates what's in `last_access_events`. Fine at this roster's scale; would need revisiting (a single windowed query) if the tracked team grows a lot.
- **npm workspace quirk**: `drizzle-orm` is listed as a root-level `devDependency` in addition to being a `backend` dependency. Without that, `drizzle-kit` (which npm hoists to root `node_modules`) can't resolve `drizzle-orm` (which otherwise stays nested under `backend/node_modules`), and `drizzle-kit generate` fails with a misleading "Please install latest version of drizzle-orm" error. Don't remove it.

### Reports

The Reports page (`/reports`) is a growing area for custom queries over `access_event_history`, separate from the live dashboard. First report: "first & last swipe by day" (`routes/reportRoutes.ts` -> `services/reportService.ts` -> `accessEventRepository.getHistoryInRange()`).

- **This report is used for payroll verification of recent employee start times**, not just an informational dashboard extra - treat its correctness and data availability as payroll-sensitive. This is also why `access_event_history` being a *pruned* log (bounded by `HISTORY_RETENTION_DAYS`, default 30) matters here in a way it didn't for the dashboard: the report can't reach back further than that window. Flag it before reducing retention further, or before any change that could shrink how far back history reaches.
- **Day-bucketing is school-local, not UTC**: `backend/src/utils/schoolTimeZone.ts` is a server-side port of the same `Intl.DateTimeFormat`/`formatToParts` technique `frontend/src/utils/schoolTime.ts` already used for "present today" shading - a UTC-stored timestamp near midnight can fall on a different `America/Chicago` calendar day than its UTC one, so grouping must go by the school-local date.
- SQLite has no timezone-aware date functions, and Chicago's DST offset (-05:00/-06:00) makes a fixed-offset SQL boundary wrong twice a year. Rather than doing that math, `reportService.getFirstLastSwipeReport()` pads the DB range query a day on each side and then filters rows back down to the exact requested range using each row's actual computed school-local date - simpler and safer than timezone-aware SQL, at the cost of fetching a bit more than strictly needed.
- `accessEventRepository.getHistoryInRange()` stays a plain range query returning raw joined rows (teamMemberId, displayName, doorName, eventTimestamp); all bucketing/grouping logic lives in `reportService`, keeping with the layering rule that only repositories touch Drizzle/SQL directly.
- **The report list is meant to grow.** `frontend/src/reports/registry.ts` is a small array of `{ id, label, Component }` that drives the Reports page's report-selector dropdown (`pages/ReportsPage.tsx`, which just picks and renders the selected `Component`). Add a new report by writing a self-contained component under `frontend/src/reports/` (its own filters/fetch/state, following `FirstLastSwipeReport.tsx`) and listing it in the registry - don't grow `ReportsPage.tsx` itself with per-report logic.
- The results table (`components/FirstLastSwipeReportTable.tsx`) supports grouping by clicking the "Date" or "Name" column header (client-side only - the API always returns rows sorted by date then name). Rows stay sorted chronologically by `firstEventTimestamp` within whichever group is active; a top-border rule marks where one group ends and the next begins. No collapsible sections - "group" here just means a visual separator in an otherwise flat list, per what was asked for when this was built.
- No `db/schema.ts` change was needed for this feature - `access_event_history` already had everything required (team member id, door name, timestamp).

### Real Avigilon ACM integration

`AvigilonAcmClient.ts` was implemented from Avigilon's official "Access Control Manager REST API" guide (v6.44, June 2023 - the customer's own PDF, not something publicly indexed) plus live verification against a real appliance. The API's actual shape differs from what you'd assume from the plan, in ways that are easy to get wrong if re-deriving this from scratch:

- **Auth is HTTP Basic on every request.** There is no login/session endpoint - `Authorization: Basic base64(user:pass)` is sent with each call (`avigilonHttp.ts`).
- **There is no "recent access events" feed at all.** The REST API's "Events" resource (`/points.xml`) is alarm/point *definitions*, not a transaction log. The only push mechanism ("Collaborations") requires ACM-side configuration we don't control from this codebase.
- **"Last door" lives on the Token record, not the Identity record.** A person can hold multiple badges (`/identities/<cn>/tokens.xml` returns one `<token>` per badge), and each token carries its own `plasecLastdoor` (a door DN, e.g. `cn=16,ou=doors,cn=...,ou=gateways,dc=plasec`) and `plasecLasttime`. The Identity record only rolls up a MAX `plasecLasttime` across all its tokens - it does not expose `plasecLastdoor` at all, because there'd be no unambiguous single door to roll up if the person holds more than one badge.
- **Resolving a badge number requires two requests, since plain `filter=` can't reach nested attributes**: `AvigilonAcmClient.resolveIdentityCn()` uses the `adv_search_field_0=plasecInternalnumber&adv_search_val_0=<badge>` mechanism against `/identities.xml` to find the owning identity's CN (cached per badge for the process lifetime), then fetches that identity's `/tokens.xml`. A plain `/identities.xml?filter=(plasecInternalnumber=X)` LDAP filter silently returns zero results for this, because `plasecInternalnumber` lives on the nested Token object, not the Identity object being filtered.
- **A person can hold multiple active badges/tokens**, each independently tracking its own `plasecLastdoor`/`plasecLasttime` - confirmed live (a real badge-in via a second token left the first token's data completely unchanged). So `getLastEventForBadge()` doesn't just read the one token matching the roster's stored badge number - it fetches *all* tokens on the resolved identity and uses whichever has the most recent `plasecLasttime` as the person's true last-known door. The stored badge number is only the lookup key for *who the person is*, not a claim that it's their only or most-used credential.
- **`plasecLastdoor` is a DN, not a name** - resolved against a cached `/doors.xml` DN→`plasecName` map (`getDoorNameMap()`, 1-hour TTL; doors rarely change so this isn't refetched every poll cycle). The fetch is memoized via an in-flight promise (`doorMapFetchPromise`), not just the resolved `Map` - otherwise every badge hitting a cold/stale cache at the same moment (they all run in parallel, see below) would each trigger their own redundant `/doors.xml` fetch instead of sharing one.
- **`getRecentAccessEvents` resolves all requested badges in parallel** (`Promise.all`), not one at a time. Each badge's *own* lookup stays sequential internally (resolve identity, then fetch its tokens - one depends on the other), but different badges are independent. Originally sequential; with the roster at 14 people, 14 back-to-back HTTPS round trips to the ACM appliance started regularly exceeding the poll interval, so cycles overlapped and got skipped by the scheduler's overlap guard (visible as repeated "Skipping poll cycle: previous cycle is still running" log lines). Watch for that log message resurfacing if the roster grows a lot further - it's the signal this needs revisiting (e.g. a concurrency cap) rather than just "more parallelism."
- **Timestamps are ACM's own format**, not ISO 8601: 14 digits (`YYYYMMDDHHMMSS`) followed by either `Z` or a signed 4-digit offset like `-0500` (e.g. `20260902140849-0500`). See `avigilonTimestamp.ts` - both forms were observed live on the same real record (`createTimestamp` used `Z`, `plasecLasttime` used the offset form).
- **The roster's "ACM Cardholder ID" field means a badge/token internal number** (`plasecInternalnumber`, e.g. `2558933` - what ACM's own UI calls a badge), not the identity's `plasecId` (an internal GUID in this deployment, not a human-assigned external ID as the API guide's field description might suggest). The frontend roster form/table label this "Badge Number" for that reason. Given the multi-token behavior above, it only needs to be *a* valid badge number for that person - not necessarily their primary or most-used one.
- **XML parsing** uses `fast-xml-parser` with `parseTagValue: false` (badge numbers must stay strings - the parser's default numeric auto-detection would silently strip leading zeros) and a `isArray` callback forcing `identity`/`token`/`door` tags to always parse as arrays, since a single-match response and a multi-match response are otherwise structurally different.
- **TLS**: ACM appliances typically present a self-signed cert; `ACM_TLS_REJECT_UNAUTHORIZED` (env, defaults `false`) controls Node's `https.Agent({ rejectUnauthorized })`, matching Avigilon's own sample client code (`OpenSSL::SSL::VERIFY_NONE`).
- **Anti-passback/Areas tracking being disabled system-wide** (no door had `plasecdoorApbinareaDN`/`Apboutarea`/`Apbmode` set, confirmed via `/doors.xml`) is *why* the Identity-level fields are empty in this deployment - that's a red herring to rule out with a live `/doors.xml` check before assuming a code bug if `plasecLastdoor` ever appears missing again.
- **`AvigilonAcmClient.getRecentAccessEvents` deliberately ignores the `since` parameter** and always returns each requested cardholder's current last-known event. Found via live testing: pre-filtering by `since` (which made sense for the mock's growing event log) hid a real person's real last-known door whenever it predated when they were added to the tracked roster, because ACM has no history to filter - only ever "current state." Deduping against what's already changed is `accessEventRepository.recordEventIfNewer`'s job (it compares against what's cached in *our* DB per person), not this client's.
- `getRecentAccessEvents` catches and logs per-badge failures (unresolvable badge, missing token, etc.) rather than failing the whole poll cycle - one bad roster entry shouldn't take down everyone else's dashboard row.
- No automated tests cover `AvigilonAcmClient` itself (it needs a live appliance); `MockAcmClient` is what all automated tests exercise. Verify changes to this file with a live poll against the real server, not just `npm run test`.

### Backend tests

Vitest, in `backend/test/`. Tests that touch the DB set `process.env.DB_PATH` to a fresh `mkdtempSync` temp file **and then dynamically `await import(...)`** the modules under test (rather than static top-level imports), so each test file gets an isolated database instead of sharing state with other test files or picking up a stale `env`/`db` singleton. Follow this pattern for any new test that touches `db/client.ts` transitively. Route tests (including the reports endpoint) all live together in `test/routes/api.test.ts`, sharing the one seeded admin/app instance per file - the reports tests there include a case that plants an event at 11:30pm Chicago time (which crosses into the next UTC calendar day) specifically to pin down the school-local day-bucketing behavior described under "Reports" above.

### Frontend

- `App.tsx` wires routes: `/login` (public), everything else behind `RequireAuth` (redirects to `/login` if `useAuth()` has no user) wrapped in `Layout` (nav + logout).
- `auth/AuthContext.tsx` checks `/api/auth/me` on mount to determine session state; `api/client.ts` is a thin `fetch` wrapper (`credentials: 'same-origin'`) shared by all API calls, typed against `@acm-tracker/shared` DTOs.
- `hooks/usePolling.ts` is the generic interval-fetch hook driving both the dashboard's team list and its health badge - deliberately plain polling (no WebSockets/SSE), matching the backend's own polling model against ACM.
- **`utils/schoolTime.ts` pins the dashboard clock and "present today" card shading to the school's fixed local time zone** (`America/Chicago`), not the viewer's browser - this dashboard is about who is physically at the school, which shouldn't shift depending on where someone views it from. `TeamMemberCard.tsx`'s "present" shading requires the swipe to be *today* (in that time zone) AND between 5am-5pm; a time-of-day match on a stale prior-day swipe deliberately doesn't count, or the dashboard would misleadingly show someone as "here" when they haven't badged in yet today. `components/DashboardClock.tsx` uses the same helpers for the header clock.
- No frontend automated tests exist; verification is manual/browser-driven (Playwright was used ad hoc during development, not wired into the repo).
